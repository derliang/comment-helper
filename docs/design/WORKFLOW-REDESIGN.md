# 評分流程改版：討論記錄

> 狀態：**討論中，未定案，未實作。** 日期：2026-11-28（台北）。這份寫給沒看過討論對話的人：結論、原因、沒採用的選項、未決事項、相關檔案。`DESIGN.md` 尚未更新；使用者說「定案」並授權實作後，才把規則寫回 `DESIGN.md`，並把草稿稿件轉成 `mockups/` 的定案模擬頁。

## 1. 使用者要的目的（原話摘要）

- 這個程式的目的是讓老師**快速對學生做出評比**，系統給評語建議，老師確認後就進行下一位。
- 平台主要目的**不是讓老師構思評語**，而是給出評定等第。
- 補充：**減少使用者捲動頁面**，一來一次看到資訊，二來節省捲動時間。

## 2. 現況查證（讀程式碼，未在瀏覽器實測）

來源：`app.mjs`（函式 `detail`、`changed`、`data-next` 處理、panel `keydown` 處理）。

1. **「確認評語」這一步不存在。** 「完成評分，下一位」只檢查六向度是否評完，不檢查老師有沒有看過評語。評分完成後焦點跳到「個別觀察」，Shift+Enter 可在評語出現前就離開；評語由 `changed()` 延遲約 0.9 秒生成，離開後才補生成。「保護評語」是選用，不屬於流程。
2. **每位學生多一次滑鼠點擊。** 換到下一位後，焦點不會自動放在第一個評分格。
3. **畫面上有太多非主線的東西。** 評語卡七個按鈕（重新生成、其他寫法、版本紀錄、AI 協助、比對歷史、複製、保護），另有快速設定、準則摺疊區、個別觀察框。
4. **評分與評語的視覺關係偏弱。** 桌機評分鍵 26px 高，評語在右欄下方。

## 3. 使用者已回答的決定

| 問題 | 回答 | 備註 |
| --- | --- | --- |
| 確認方式 | **接受並下一位**：評完六分，評語立即出現，老師看過按一下才跳下一位 | 否決「評完自動下一位、事後再看」（老師逐位看不到評語） |
| 主要輸入 | **滑鼠點評分鍵**、**手機或平板觸控**（不含鍵盤連按） | 設計重心是評分鍵大小與點擊次數 |
| 評語卡按鈕 | **主線只留三個**：接受並下一位、重新生成、其他寫法；其餘收進「更多」 | 功能都保留 |
| 個別觀察 | **預設收起**，需要時才展開 | 桌機與平板放標題列「＋ 補充觀察」；手機收進「⋯」 |
| 方案 | **採 1A「評分＋評語並排」** | 保留左側名單；中間左評分、右評語建議 |
| 手機評分鍵 | **可以縮為 44px**，並省略五級文字色階列 | 規範原為 48px，屬偏離，見〈5〉 |
| 新增要求 | **桌機、平板、手機都一屏放完，不捲動** | 見〈4〉 |
| 桌機評分鍵（2026-11-28 問題卡） | **採 44px**（現行 26px） | 稿件已量測筆電 650px 高度仍一屏放得下 |
| 手機可視高度低於約 664px | **評語區內部捲動**；評分與「接受並下一位」固定可見 | 否決：評分鍵再縮到 40px（低於最小點擊目標）、不特別處理 |
| 評語生成中（約 0.9 秒） | **評語出來前，「接受並下一位」停用** | 否決：可直接按、評語事後補生成（會讓老師沒看到評語就跳過） |
| 與 T3、L3 的順序 | **先驗收 T3，再改版**；L3 照原決定等 T3 驗收後再議 | 否決：直接改版並作廢 T3、兩者分開進行 |

## 4. 一屏預算（我的估算，不是使用者給的數字）

| 裝置 | 稿件高度 | 依據 | 量測結果 |
| --- | --- | --- | --- |
| 桌機 | 1280×650 | 1366×768 筆電瀏覽器可視高度約 650 | 無溢出 |
| 平板 | 820×960 | 暫估 | 無溢出 |
| 手機 | 390×664 | 一般手機可視高度約 664 | 無溢出，1A 餘裕僅約 13px |

比 664px 更矮的手機（例如舊款 iPhone SE）會被擠出捲動，降級做法已決定：評語區內部捲動，評分與主按鈕仍固定可見（見〈3〉）。名單（桌機）有自己的內部捲動，應把目前這位自動帶到可見位置。

## 5. 與現行規範的偏離（實作前必須先更新 `DESIGN.md`）

- 手機評分鍵 48px → 44px；手機省略五級文字色階列。使用者已同意。
- 桌機評分鍵 26px → 44px：使用者已同意（2026-11-28 問題卡）。規範〈4〉原註明不得為放大評分鍵而讓單頁免捲動失效；稿件已量測桌機 650px 高度仍無溢出，實作時須同步更新該段評估。
- 「補充觀察」入口位置改變（標題列／手機「⋯」）。
- 「接受並下一位」取代現行「完成評分，下一位 →」，且須在評語出現後才可按；與 2026-11-26「不需要鎖定評語」不衝突，因為「接受」不鎖定，教師之後仍可改。
- 規範〈4〉情境列「主按鈕顯示下一位姓名」（L3）仍等 T3 驗收後再議，這次沒有處理。

## 6. 未採用的方案

- **1B 單張大卡（觸控優先）**：名單縮成上方座號圓點，平板評分鍵 52px。原因：使用者選 1A。手機放不下圓點列，已知會沿用 1A。
- **1C 整體＋例外**：先點整體分數，只改不一樣的向度，點擊 2～5 次。原因：使用者選 1A；風險是老師不細看就整體套用，若日後重提需先決定「套用的預設算不算已評」。

## 7. 實作順序與未決事項

**順序（使用者已決定）**：先請使用者驗收 T3（UI 回饋 6 項，見 `UI-ISSUES.md`），驗收後才開始這次改版；L3（主按鈕顯示下一位姓名）照原決定，等 T3 驗收後再議。在那之前不改程式、不改 `DESIGN.md`。

**仍未決**：

1. 是否取消現行約 0.9 秒的延遲生成（`changed()` 的 `setTimeout`）。我的建議：生成在本機執行，不需等網路，可取消延遲，讓評語在評完最後一個分數時立即出現；但這是建議，使用者尚未回答。（「評語出來前按鈕停用」已決定，見〈3〉。）
2. 「接受並下一位」之後，焦點與名單捲動位置的行為（目前換學生後焦點不會自動放在第一個評分格）。
